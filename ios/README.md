# LightCraft for iOS (prototype)

A SwiftUI app over the Rust develop pipeline that looks and works like the desktop app's Edit view:
pick a photo, edit it with the Light (Exposure … Blacks) and Color (Temp, Tint, Vibrance, Saturation)
sliders, Auto and B&W, compare before/after, and export a JPEG to Photos. Previews render on the GPU
(wgpu → Metal) and fall back to the CPU pipeline.

```
ios/
  Cargo.toml              own Cargo workspace (outside the main one: `cargo xtask ci` never sees it)
  lightcraft-ffi/         Rust bridge, exposed to Swift with uniffi
  tools/gen-theme/        writes the app's design layer from the desktop UI crate (runs on the Mac)
  build-xcframework.sh    design layer + static libs (device + simulator) → build/LightCraftFFI.xcframework
  app/project.yml         XcodeGen spec for the app
  app/LightCraft/         SwiftUI sources
  app/Generated/          generated, not committed: bindings, Theme.generated.swift, Icons.xcassets
```

## Build and run

Needs Xcode, rustup (`brew install rustup`, then put `/opt/homebrew/opt/rustup/bin` on `PATH`)
and XcodeGen (`brew install xcodegen`).

```bash
ios/build-xcframework.sh          # after every change to the Rust side
cd ios/app && xcodegen            # after adding/removing Swift files
open ios/app/LightCraft.xcodeproj
```

To run on a device, choose your team under Signing & Capabilities (or set `DEVELOPMENT_TEAM` in
`project.yml`). Rust tests run on the Mac: `cd ios && cargo test`.

If this checkout is inside an iCloud-synced folder (Desktop/Documents), keep Xcode's DerivedData
in its default location: `codesign` rejects the extended attributes iCloud adds.

## Looks and works like the desktop app

The iOS screen is the desktop's Detail view: top bar, photo canvas, and the Edit panel (histogram with
the capture line, Edit + Auto / B&W / Reset, collapsible Light and Color sections). The panel sits on
the right on iPad and in landscape, under the photo on iPhone in portrait.

- **Same design, generated.** `tools/gen-theme` links `crates/ui-egui` and writes
  `Theme.generated.swift` from `theme::Tokens` (all four desktop themes: Charcoal, Midnight, Silver,
  Paper) and `Icons.xcassets` from the desktop's own icons (`icons.rs`, painted with egui and saved as
  vector SVG), plus the app icon from `assets/app-icon`. The UI font is Inter, bundled from
  `assets/fonts` in place.
- **Same controls, from Rust.** Sections, slider labels, ranges, steps, value text, track colours,
  typed values and nudges come from `lightcraft-ffi` (`panel_sections`, `format_value`, …), which
  reads `develop::controls`; Swift names no control. Temp/Tint use the desktop's relative scale for
  rendered photos.
- **Same gestures, for touch.** Drag the row (relative: a touch never jumps the value), double-tap to
  reset, tap the value to type one, press and hold the photo (or the Before/After button) to see the
  original. Appearance (top bar): Auto / Light / Dark with a theme per family, as in the desktop's
  Settings ▸ Interface. VoiceOver adjusts sliders by the desktop's arrow-key step.

### Pulling from upstream

Most design and control changes upstream flow through by themselves on the next
`ios/build-xcframework.sh`: tokens, themes, icons, control specs, Auto's recipe values.

A few values live upstream as literals in widget code and are mirrored here (slider and section
geometry, histogram colours, the relative white balance formula, which sliders each section shows…).
Each mirror cites its upstream line in `tools/gen-theme/src/main.rs` (`MIRRORS`); the build fails when
one of those lines changed, naming the value to update. A token added to `Tokens` stops the generator
compiling until it is listed. Check without building: `cd ios && cargo test` (also runs the bridge's
tests), or `cargo run -p gen-theme -- --check ..`.

## Design notes

- **Bridge, not engine.** `lightcraft-ffi` calls `codecs` → `pipeline` / `gpu` directly, the same
  render path the engine uses, without the catalog, settings folders and desktop paths a one-photo
  editor doesn't need. Export encodes with `codecs::encode_jpeg` rather than `engine::export`.
- **Memory.** The photo is decoded straight to a capped working size (3072 px long edge by
  default, 6144 max; JPEG uses DCT-domain downscaling) and that is also the export size, for now.
  The GPU buffer pool is limited to 256 MB.
- **HEIC** is transcoded to JPEG by ImageIO before decoding, unless the bridge is built with
  `FEATURES=heif` (pure-Rust HEIC, off by default for the same patent reason as the desktop builds).
- **Never crash.** Every export returns `Result`, so a Rust panic surfaces in Swift as a thrown
  error. The Swift side never uses `try!`. The `unsafe` FFI glue is generated by uniffi;
  hand-written Rust in the bridge is safe.
- **Not yet:** the Profile and White Balance pickers, Curve and the other flyouts/sections, HDR,
  history (undo), presets, the library and filmstrip. Text uses the desktop's fixed sizes (no
  Dynamic Type yet).
